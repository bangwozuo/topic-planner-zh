# 使用示例

以下示例 1-2 来自 `scripts/radar_scan.py` 对 `examples/input.json` 的实跑结果
（退出码 0，2026-09-30）；示例 3-5 为模型侧（纯提示词路）的典型场景。

## 示例 1：标准输入 —— 12 条热榜 → 10 个话题的四级分档

**输入**（节选，完整见 `examples/input.json`）：

```json
{
  "date": "2026-09-30",
  "entries": [
    {"title": "00后整顿职场：拒绝无效加班从这3句话开始", "platform": "抖音", "heat": 1860000, "rank": 2, "hours_since": 9},
    {"title": "00后整顿职场，拒绝无效加班的3句话", "platform": "小红书", "heat": 92000, "rank": 5, "hours_since": 14},
    {"title": "某地突发地震，多地震感明显", "platform": "微博", "heat": 2100000, "rank": 1, "hours_since": 3},
    {"title": "前同事裁员的那个下午，我在工位学到的3件事", "platform": "知乎", "heat": 22000, "rank": 19, "hours_since": 200}
  ]
}
```

**输出**：`out/热点候选池.xlsx` + `out/热点平台分布.png` + `out/radar_scan.json`。
12 条 → 合并 10 个话题：A 级 1 / B 级 5 / C 级 3 / 红线 1。
Top1「00后整顿职场」因跨抖音+小红书两平台（热度上浮 10%）且命中职场赛道词表，
得 101.8 分判 A 追，备注「24h 内出稿抢占先机」。

## 示例 2：整改前后对照 —— 从「凭感觉刷榜」到「按半衰期追热点」

| 阶段 | 做法 | 结果 |
|---|---|---|
| 改造前 | 每天早上刷 1 小时各平台热榜，凭「感觉这个能蹭」挑题，常追已挂榜 3 天的旧热点 | 写出来就过时；追「9.9 包邮内幕」这类超 48h 的题，发布时热度已衰减一半以上 |
| 改造后 | 07:30 跑一次雷达脚本 → 候选池按半衰得分排序 → 只做 A 级与「泛题切垂直角度」的 B 级 | 「00后整顿职场」9h 内出稿抢到搜索红利；灾难类、明星类不再误入选题 |

**关键差异**：热梗半衰期 48h 是铁律——超 48h 未跨平台扩散的题，
衰减系数已降到 0.67，同样两小时制作成本，回报差一倍以上。

## 示例 3：跨平台合并的价值（真实机器判定）

「00后整顿职场：拒绝无效加班从这3句话开始」（抖音 186 万）与
「00后整顿职场，拒绝无效加班的3句话」（小红书 9.2 万）标题表述不同，
若不做合并会被当成两个候选。脚本按去标点二元组相似度（0.74 ≥ 0.55 阈值）
合并为同一话题，平台数计 2、热度分上浮 10%——跨平台扩散是「真热点」
的最强信号，单平台挂榜可能只是该平台的运营位。

## 示例 4：灾难热点标红线（合规拦截）

「某地突发地震」热度归一 100.0，全场最高，但命中风险词表 → 判 R 红线，
备注明确「不蹭，仅做无关内容排查」。它的作用是反向的：如果本周已排期的
视频选题与地震话题撞车（如一条轻松向职场视频），需要考虑延期发布，
避免在灾难氛围里发娱乐内容引发反感。

## 示例 5：空数据不猜

**输入**：`entries: []`（当天只截到 1 个平台的榜，用户忘了粘贴其余平台）。

**输出**：脚本报错 `entries 为空` 并退出（退出码 1），不输出编造的候选池；
模型路则按 prompt 要求列出「缺失信息源清单」（微博/知乎/B站未采集），
请用户补齐后再跑。宁缺勿编——错的热点数据比没有数据浪费更多制作时间。
